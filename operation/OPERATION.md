# Platform Operation

Status: Approved

## 1. 運営前提

- 管理者1人
- PCで管理
- 想定利用者100〜300人
- 手動対応を許容
- 毎日の定型確認を極力なくす
- 問題が起きた時だけ対応する

## 2. 日常運用

通常は作業なし。

以下の通知が来た場合のみ確認する。

- Warning
- Stripe決済異常
- ユーザー問い合わせ
- Cloudflare障害通知
- Supabase障害通知

## 3. 問い合わせ対応

基本手順:

1. メールアドレス検索
2. ユーザー詳細表示
3. 商品権限確認
4. 購入履歴確認
5. note移行履歴確認
6. ログ確認
7. 必要な操作をボタンで実行

## 4. 商品権限

管理画面から以下を実施できる。

- 手動付与
- 停止
- 再開
- 開始日修正
- 終了日修正
- MEMO更新

## 5. 購入

Stripe購入はWebhookで自動反映する。

未反映問い合わせ時:

1. Stripe側確認
2. Checkout Session ID確認
3. T_PURCHASE確認
4. Webhook再送
5. 必要なら手動補正

## 6. note移行

通常は利用者による自己移行。

例外は管理画面から手動紐付けする。

## 7. ログ

ログ件数が増えて検索が遅くなった場合だけ整理する。

手順:

1. CSV出力
2. 保管
3. 対象期間確認
4. 古いログ削除
5. 件数確認

初期段階で自動ローテーションは実装しない。

## 8. 固定費

既存固定費:

- ドメイン
- Cloudflare Workers Paid

売上発生時のみ:

- Stripe決済手数料

無料枠を基本:

- Supabase

新たな固定費は、既存環境で代替できない場合のみ追加する。

## 9. 退会

初期は利用者向け退会画面を必須としない。

依頼があった場合は管理者対応可能とする。

購入履歴・権限履歴を即時物理削除しない。

法令・規約上の保存要件はリリース前に確認する。

## 10. サービス終了

買い切り商品のため、サービス終了時は十分な告知期間を設ける。

終了時に検討する内容:

- 新規販売停止
- 利用者告知
- データエクスポート
- オフライン利用の扱い
- 最終サポート日
- 個人情報削除
- ドメイン・Cloudflare停止時期


## 11. 正式DEV運用

Productionで試して直さない。変更はLocal→DEV→Productionの順で昇格する。DEVは専用D1・Stripe Test・Cloudflare Accessを使用し、`https://shingo-camera.com/dev/*`内で認証・購入・アプリ起動まで確認する。

テスト購入をやり直す場合、管理者用DEV reset APIを利用できるが、Productionではdenyされることを維持する。Stripe Checkout後はreturn URL、購入権反映、「利用する」起動先、自前API Request URLに`/dev`が維持されることを確認する。

古い修正ZIPをcurrent sourceへ丸ごと上書きしない。成果物適用前にdiffを確認し、後から入った修正の巻き戻しがないことを確認する。
